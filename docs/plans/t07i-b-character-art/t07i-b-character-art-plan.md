# Plan — t07i-b-character-art (T-07i-b · Імпрувмент прологу №2: візуал персонажів)

## Goal
Replace the four coloured rectangles that currently stand in for people (`PH_Body` / `PH_Face` /
`PH_Fist` in `Player`, `Guard`, `Dummy`, and the flat `PH_Dan` figure in the prologue) with one
shared, procedurally-coloured human silhouette — head, torso, two arms, two legs, a dark outline
and a facing mark — plus real skeletal animation for idle (breathing), walk, jump, the three light
attacks, the heavy attack, hurt and KO. Everything is built in-engine from `Polygon2D`/`Line2D`
(the author's 2026-09-09 decision recorded in
[`../t07i-visual-kit/visual-brief.md`](../t07i-visual-kit/visual-brief.md)); no files are added to
`assets/`. Characters differ by **colour and build only** — one `CharacterRig.tscn` serves the
hero, the guard, the training dummy and Dan. The project palette moves into a single
`scripts/art/Palette.cs`. Combat balance is untouched: every animation keeps its current length
and its `HitboxOn`/`HitboxOff` method-track times to the millisecond, and every `Hitbox`/`Hurtbox`
keeps its shape, position and parent. Task: [`../../TASKS.md`](../../TASKS.md) → **T-07i-b**.

## Design-doc conformance
- **`GAME_DESIGN.md` §6 «Арт-напрям (hand-painted 2D, референс — Streets of Rage 4)»** is the
  section this task serves. It asks for: characters with a clear outline (`Обводка`), animation
  with anticipation and a held frame on impact, flat shadows, cold concrete + warm energy accents,
  and per-frame animation counts (idle 8, walk 8, light attack 4–6, heavy 8, hurt 4, KO 6).
- **Documented deviation, already decided by the author:** §6 assumes *hand-painted sprite sheets
  generated by an art agent* plus normal maps. The T-07i brief (author's decision of 2026-09-09)
  overrides this for now — "Арт — процедурний, у движку… Ніяких файлів-картинок" — and requires the
  `Visual/Sprite` (`AnimatedSprite2D`) slot to stay in every character so a sprite sheet can
  replace the rig later. This plan follows the brief; §6's principle (silhouette, outline,
  anticipation, flat shadow, warm hero / cold enemies) is honoured, its *medium* is deferred.
  No new question for the author.
- **Second documented deviation:** CLAUDE.md requires placeholder visuals to carry the `PH_`
  prefix. The brief's rig contract names the nodes `Rig / LegBack / ArmBack / Torso / LegFront /
  Head / Face / ArmFront / Fist / Outline` **without** the prefix, because these are the intended
  in-engine graphics, not placeholders. Following the brief. `PH_Shadow` keeps its name and its
  place as a direct child of the character root (brief + T-B01 author decision).
- Task text vs. the brief: **they agree**. The brief additionally pins the palette table, the rig
  node tree, the `[Export]` names, and the compatibility list; this plan does not restate or
  rewrite any of it, it plans against it.
- Author decisions from [`../../sessions/2026-09-09-session-01.md`](../../sessions/2026-09-09-session-01.md)
  §3 that constrain this task: floored enemies are invulnerable and lie for `DownDuration` (the
  rig must lie down with them, not keep walking); `Visual/Hurtbox` stays under `Visual` so a jump
  lifts it; the hero's KO rule is untouched.

## Options considered

### 1. Polygon geometry authored in `CharacterRig.tscn` vs. generated in `_Ready`
| | (A) Authored in the `.tscn`, `_Ready` applies colour + build | (B) All points generated in `_Ready` from `Build` |
|---|---|---|
| Editor preview | Shows a person immediately; the author can nudge a vertex by hand | Empty node until the game runs — bad for a task whose whole deliverable is "does it look like a person" |
| `Build` expressiveness | Scale/offset per part (width, limb thickness, attach points) | True re-proportioning (different shoulder curve per build) |
| Tuning loop | Edit `.tscn` (hand-written text, error-prone) or drag in the editor | Edit C# constants, rebuild |
| Per-frame cost | none | none (one-time) |
| Risk | A hand-written polygon array with a typo is a silent visual bug | A geometry bug is invisible until run; more code to review |

**Chosen: (A) with a thin (B) layer.** The nine part polygons are authored in
`CharacterRig.tscn` for the `Normal` build so the scene previews correctly in the editor;
`CharacterRig._Ready()` applies (i) the `[Export]` colours with per-part shading and (ii) the
`Build` factors as `scale` / `position.x` multipliers on the parts. Only the **front arm** is
rebuilt procedurally, because it must reach from the shoulder to a fist whose position an
animation moves from 13 px to 46 px away (see option 3).

### 2. One rig with exports vs. one scene per character
| | (A) One `CharacterRig.tscn`, colour + build via `[Export]` | (B) `PlayerRig.tscn` / `GuardRig.tscn` / … |
|---|---|---|
| Brief | Explicitly required ("Персонажі відрізняються **кольором і статурою**, не окремими сценами") | Contradicts the brief |
| Consistency | A silhouette fix lands everywhere at once | Four places to fix; drift guaranteed |
| Per-character quirks | Needs an export for anything that differs (e.g. the faceless dummy) | Free |
| Scene count | 1 | 4 |

**Chosen: (A)** — it is the brief's contract, and the only per-character quirk found in the code
is the training dummy's centred (faceless) patch, covered by one boolean export.

### 3. How the front arm follows the animated fist
The existing attack animations move `Visual/PH_Fist:position` from `(14,-10)` (guard pose, 13 px
from the shoulder) to `(34..48, -10)` (full extension, up to 46 px). The brief's contract puts
only `Fist` under `ArmFront`, so there is no separate upper-arm node to rotate.
- **(A) Fist only, no arm** — what we have today, a floating hand with a 36 px gap to the torso at
  full extension. Rejected: this is precisely the "rectangle" problem the task exists to fix.
- **(B) Rotate + `scale.x` a sleeve polygon** — a 3.5× stretch between guard pose and extension,
  so the hand blob stretches into a 35 px sausage. Rejected.
- **(C) Rebuild `Fist.Polygon` each frame** (chosen): `CharacterRig._Process` writes a cached
  9-vertex buffer — a hand octagon around the fist origin plus a tapered quad back to
  `ShoulderAnchor` (converted into `Fist`-local space) — into `Fist.Polygon`. No node rotation, no
  distortion, correct at every extension, ~15 float ops per character per frame, one `Vector2[]`
  allocated once in `_Ready`, and an early-out when `Fist.Position` has not moved since the last
  frame (idle and hit-stop frames cost one comparison). The animation key **values stay byte-for-
  byte identical** — only the track's NodePath changes — so nothing about reach or timing moves.
- **(D) Change the fist key values so a fixed-length arm works** — would rewrite animation data the
  author has already playtested, for no gain. Rejected.

### 4. Where the "lean" of the `hurt` animation goes
`hurt` and `RESET` currently drive `Visual/PH_Body:rotation`. `Visual:rotation` is **not** free —
`ko` uses it and `Guard.SetDown()` / `Dummy.SetDown()` write it directly. Retargeting the lean to
`Visual/Rig:rotation` reproduces the old pivot exactly (the old `PH_Body` polygon was centred on
the `Visual` origin, and `Rig` sits at the same origin) and keeps `Visual:rotation` owned by
knockdown/KO. Chosen. Rotating `Torso` alone was rejected — `Head` is `Torso`'s sibling in the
brief's tree, so the head would stay put and the character would decapitate itself on every flinch.

## Recommended approach
1. `Palette.cs` first (no dependencies), then `CharacterRig.tscn`/`.cs` standalone, then the four
   consumer scenes, then the animations, then the tests.
2. The rig's local origin **is** the `Visual` origin: body centre, feet at `y = +36`, top of head
   at `y = −36` — the same 72 px box `PH_Body` occupied. This keeps `SpriteFeetOffset = 36`, the
   32×64 hurtbox, the 36×40 hitbox at `(30, 0)` and the guard's ~52 px jump-dodge threshold valid
   without touching a number (`tests/smoke/enemy_guard.gd` asserts that geometry).
3. `Rig.position = (0,0)` and `ArmFront.position = (0,0)`, so the retargeted
   `Visual/Rig/ArmFront/Fist:position` track keeps the current key values.
4. Facing is unchanged: `Player.UpdateVisual()` and `Guard.UpdateVisual()` set
   `Visual.Scale = (Facing, 1)`. The rig is a child of `Visual`, so it mirrors as a whole — the
   `Face` wedge, the front leg/arm and the fist all flip together. `CharacterRig` never reads
   facing and must never write `scale.x` on `Rig` itself (that would fight the flip).
5. `_Ready` applies colours and build; `_Process` maintains the front arm only.
6. Animations live on each character's existing `AnimationPlayer`; the rig scene ships **no**
   `AnimationPlayer` of its own (one owner per animation, and the hero/guard players already exist).

## GameState & save impact
**No GameState change.** No field is read or written, no signal is added or emitted, nothing new
needs persisting in T-09. `Palette` is a static class of `Color` constants — compile-time data, not
runtime state, and deliberately *not* an autoload (it holds no state and needs no node).

## Scene & signal contract

### New scene — `scenes/actors/CharacterRig.tscn` ↔ `scripts/actors/CharacterRig.cs`
`public partial class CharacterRig : Node2D`, namespace `BlackoutLastGrid.Actors` (matches
`Player`/`Flashlight`, which also live in that namespace from `scripts/player/`).

Node tree — order is the draw order (no `z_index` anywhere; `y_sort_enabled` stays **false** on
`Rig` so its children draw in tree order while the level still y-sorts the character root):

```
Rig                 CharacterRig (Node2D)      position (0,0) in Visual space
├── LegBack         Polygon2D   pos (-3, 10)   hip pivot; polygon spans y 0..26
├── ArmBack         Polygon2D   pos (-3,-14)   shoulder pivot; polygon spans y 0..22
├── Torso           Polygon2D   pos ( 0,  0)   shoulders y=-16 … hips y=+12
├── LegFront        Polygon2D   pos ( 3, 10)   hip pivot
├── Head            Polygon2D   pos ( 1,-25)   octagon r≈11 → spans y -36..-14
├── Face            Polygon2D   pos ( 0,  0)   brow/visor wedge on the +x (facing) side of the head
├── ArmFront        Node2D      pos ( 0,  0)   pivot at the rig origin — keeps the fist keys intact
│   └── Fist        Polygon2D   pos (14,-10)   rest pose; hand + forearm, rebuilt each frame
└── Outline         Line2D      closed contour of Head+Torso, width = OutlineWidth
```

`[Export]` table (defaults are the values the standalone scene ships with):

| `[Export]` | Type | Default | Unit / meaning |
|---|---|---|---|
| `SuitColor` | `Color` | `Palette.SteelCold` (`#4d5866`) | Torso, limbs (shaded per part) |
| `SkinColor` | `Color` | `Palette.SkinWarm` (`#d9a077`) | Head, hand/forearm |
| `OutlineColor` | `Color` | `Palette.OutlineDark` (`#0a0d14`) | `Outline.default_color`, `Face` |
| `Build` | `enum BuildKind { Slim, Normal, Heavy }` | `Normal` | body proportions |
| `OutlineWidth` | `float` | `2.0` | px (brief: 2 px for characters) |
| `ShowFace` | `bool` | `true` | *addition* — `false` hides `Face` (the training dummy is faceless) |
| `BackLimbShade` | `float` | `0.60` | `SuitColor` multiplier for `LegBack`/`ArmBack` |
| `FrontLimbShade` | `float` | `0.85` | `SuitColor` multiplier for `LegFront` |
| `ShoulderAnchor` | `Vector2` | `(2, -16)` | px, rig-local origin of the front arm |
| `ArmWidth` | `float` | `5.0` | px, half-thickness of the forearm quad |
| `HandRadius` | `float` | `6.5` | px, radius of the hand octagon |
| `LegBack` … `Outline` | node refs | set in the `.tscn` via `node_paths` | one `[Export]` per part, repo convention (as in `Player.tscn`) |

`Build` → factors applied in `_Ready` (no magic numbers in method bodies; the three rows live in a
`static readonly` table keyed by `BuildKind`):

| `Build` | body `scale` (Torso, Outline, Head) | limb width `scale.x` | limb attach `position.x` × |
|---|---|---|---|
| `Slim` | `(0.88, 1.02)` | `0.85` | `0.88` |
| `Normal` | `(1.00, 1.00)` | `1.00` | `1.00` |
| `Heavy` | `(1.18, 0.97)` | `1.20` | `1.18` |

`ArmWidth` and `HandRadius` are multiplied by the same limb-width factor before the arm is built.

**Signals:** none. The rig is pure graphics; it emits nothing, subscribes to nothing, and never
reaches outside itself (`GetNodeOrNull` on its own children only, cached through `[Export]` refs).
**Collision layers:** none — no `Area2D`, no `CollisionShape2D` in the rig.
**Public API** (called by nobody today, kept minimal): `void Apply()` — re-applies colours and
build; called from `_Ready`, exposed so a future `[Tool]` pass (T-B06) or a test can force it.

**Lighting note (brief §"Що робить кожна задача" / GAME_DESIGN §6).** A `Polygon2D` under a
`PointLight2D` is lit uniformly, so a single-colour silhouette inside the flashlight cone would
flatten into one bright blob. Mitigation without a shader or a normal map, and without new
dependencies: shading is **baked into the parts** — back limbs at `BackLimbShade` (0.60), front leg
at `FrontLimbShade` (0.85), torso at full `SuitColor`, head/hand in `SkinColor` (a different hue
entirely), the `Face` wedge and the 2 px `Outline` in `OutlineDark`. Five distinct values plus a
dark contour keep the figure legible at full light and at `CanvasModulate` darkness alike. A real
gradient/rim-light shader is filed as backlog **T-B07**, not attempted here.

## Animations on the rig
All animation data lives in each character's existing `AnimationPlayer` (`Player.tscn`,
`Guard.tscn`). **No length and no method-track time changes anywhere.** Every property listed
below is rig-internal (`Visual/Rig/...`) except where the table above says otherwise — this is a
hard rule: `Visual:modulate` is owned by `hurt` and by the enemies' flash tween, `Visual:rotation`
is owned by `ko` and by `SetDown()`; a looping `idle`/`walk` must never touch either, or breathing
would erase a knockdown pose.

**Anticipation and return (SoR4 principle), without touching key values.** The task asks for
anticipation on the light attacks and a longer wind-up on the heavy. The *timings* that produce it
are already in the data and are frozen: `heavy` spends 0.22 s reaching the fist's extreme against
`light_1`'s 0.08 s, and the guard's `attack` pulls the fist back to `(-4,-12)` before striking.
What the rig adds for free is that the whole arm now travels with the fist, so the same keys read
as a wind-up and a recovery instead of a square sliding sideways. Any *new* anticipation must come
from **new tracks on rig-internal properties only** (`Torso:position.x` −1 px during the wind-up
window, `LegFront:rotation` +0.08 on the follow-through) — never from moving an existing key or
changing a length.

### Godot traps to respect (session §5)
- `AnimationPlayer.Play()` on the animation that is already playing does **not** rewind.
  `Player.PlayAnimation` and `Guard.PlayAnimation` already do `Play` + `Seek(0, update: true)`;
  do not "simplify" that away when adding `idle`/`walk`.
- Adding `idle`/`walk`/`jump` to the `AnimationPlayer` changes which branch `Player.PlayAnimation`
  takes: today `idle`/`walk`/`jump` fall through to the empty `Sprite` and do nothing; from now on
  they play on the `AnimationPlayer`. That is intended — but it means `PlayerIdle`, `PlayerMove`,
  `PlayerJump`, `PlayerInteract` and `PlayerHurt` start driving real animation without any code
  change, so re-check them: `PlayerAttack.PhysicsUpdate` ends an attack via
  `Player.IsAnimationPlaying(AnimationName)` (attacks are non-looping → unaffected), and
  `Player.AnimationTime` is only read inside attacks.
- `Guard.ResetPose()` deliberately calls `Stop(keepState: true)` after `RESET`, so nothing plays
  afterwards; **never** read `Guard.AnimationPlayer.CurrentAnimationPosition` after it (it prints
  `ERROR:`). `Player.ResetPose()` deliberately does **not** stop — `combat_dummy.gd` asserts
  `AnimationTime == 0` right after it.
- Ordering trap in `GuardDown.Enter`: `RESET` keys `Visual:rotation = 0`, so `ResetPose()` must be
  called **before** `SetDown(true)`, never after — calling it after is exactly the T-06 Round-1
  bug where a guard knocked down mid-swing stood back up.
- During hit-stop `Engine.TimeScale = 0`: physics steps arrive with `delta == 0` and the
  `AnimationPlayer` is frozen. `CharacterRig._Process` must not use `delta` (it does not) and its
  early-out makes a frozen frame free.
- `GuardAttack.PhysicsUpdate` ends the attack on `AnimationPlayer.IsPlaying() == false` and
  comments that comparing `CurrentAnimation` would allocate. A looping `idle`/`walk` is only ever
  started by `GuardIdle`/`GuardApproach`, never during `Attack`, so this stays correct — do not
  "helpfully" restart `idle` from `Guard.cs`.

## Performance & frame budget
- **Per character:** 8 `Polygon2D` + 1 `Line2D` + 1 empty `AnimatedSprite2D` = 10 canvas items,
  up from 3–4. With the prologue's worst case (hero + 2–3 guards + Dan) that is ~50 draw items on
  the game plane — negligible next to the level's props, and all of them are flat untextured
  polygons.
- **`CharacterRig._Process`:** one `Vector2` comparison per character per frame; when the fist has
  moved, ~15 float ops and one write of a cached 9-element `Vector2[]` into `Fist.Polygon`. The
  buffer is allocated once in `_Ready` — **no managed per-frame allocation**, no LINQ, no strings,
  no closures (the `Polygon` setter still marshals the buffer into a `PackedVector2Array`, which
  is unavoidable for `Polygon2D`). *Corrected after implementation (review S1/S2):* the shipped
  `idle` keys `ArmFront/Fist:position` with a ±1 px breathing sway, so for a character an
  `AnimationPlayer` is driving the early-out effectively never fires — the rebuild runs every
  frame. It still costs ~15 float ops on 4–5 characters, i.e. nothing; the early-out now covers
  only characters nothing animates (Dan, the training dummy, and a rig hidden behind future
  sprite art). Nothing else runs per frame in the rig; colours and build are applied once in
  `_Ready`, which also raises `process_priority` above the default so the arm is rebuilt from the
  animation's *current* fist position rather than the previous frame's.
- **Physics vs. render tick:** the rig does no physics, no queries, no `MoveAndSlide`, and holds no
  `Area2D`. Everything it does is visual → `_Process`, per CLAUDE.md. Hit detection, depth checks
  and state transitions stay exactly where they are, in `_PhysicsProcess`.
- **`GuardApproach`** gains one cached `bool` compare per physics tick per guard and calls
  `PlayAnimation` only on a walk/stop transition — no `Play` per frame, and the `StringName`s are
  `static readonly` so nothing is allocated (this is the same reason `GuardAttack` avoids reading
  `CurrentAnimation`).
- **Lights and y-sort:** unchanged. No new `PointLight2D`, no shadow-casting light, no extra node
  directly under the y-sorted level parent (the rig nests inside each character's `Visual`, and
  `Rig.y_sort_enabled` stays `false` so its parts draw in tree order).
- **Node lookups:** every rig part is an `[Export]` node reference resolved by the scene, cached in
  `_Ready`; no `GetNode` per frame anywhere.

## Risks
- **Hand-written `.tscn` animation retargeting.** Nine tracks across two scenes change their
  NodePath while their key arrays must stay identical. A typo silently breaks an attack (the fist
  stops moving) or, worse, leaves a track pointing at a dead path — Godot only warns. Mitigation:
  criteria 6–8 are asserted by the smoke tests track-by-track, and `combat_dummy.gd`'s existing
  combo/hit-stop assertions fail if a method track is disturbed.
- **`uid` correctness for the new scene.** Invented uids are invalid (session §5). Generate with
  `ResourceUID.create_id()` and run `godot --headless --path . --import` before the headless load.
- **Looping animations colliding with direct property writes.** `Guard.SetDown()`,
  `Guard.SetDimmed()` and the flash tween write `Visual.rotation` / `Visual.modulate` outside the
  `AnimationPlayer`. If a looping `idle`/`walk` ever keys those, a knockdown or a hit flash gets
  erased mid-frame. The plan forbids it and criterion 7 asserts it.
- **`GuardDown` ordering.** Calling `ResetPose()` after `SetDown(true)` re-runs the T-06 Round-1
  bug (guard stands up mid-knockdown). The characterization test (criterion 11) is written before
  the edit for exactly this reason.
- **Editor preview drift.** Without a `[Tool]` script the editor shows the rig in its neutral
  `.tscn` colours, not each character's palette colour; the author only sees the real colours in a
  run. Accepted for this task (a broken tool script can take the editor down); filed as T-B06.
- **Flat lighting.** Even with baked per-part shading, a strong `PointLight2D` will compress the
  figure. If the playtest says it still reads as a blob, the fix is T-B07 (shader/rim-light), not
  more polygons in this task.
